Employee Leave Management

Problem:

Banyak perusahaan berskala menengah masih mengandalkan cara manual (kertas, email, atau spreadsheet) untuk melacak sisa cuti dan proses persetujuan cuti karyawan. Hal ini sering menimbulkan masalah seperti:

  • Kesalahan Data: Perhitungan sisa cuti yang tidak akurat.
  • Bentrok Jadwal: Karyawan sering mengajukan cuti di tanggal yang saling tumpang tindih.
  • Birokrasi Lambat: Proses persetujuan memakan waktu lama karena kurangnya pelacakan real-time.

Action & Result:

Untuk menyelesaikan masalah tersebut, saya merancang dan membangun sistem manajemen cuti berbasis web yang terotomatisasi secara end-to-end.

  • 100% Zero-Error Tracking
  • 3 Tingkat Akses (RBAC)

Key Highlights:

  • Architecture & Database: Merancang skema database relasional di PostgreSQL menggunakan UUID, relasi Foreign Key yang ketat, dan mekanisme auto-provisioning untuk saldo cuti.
  • Role-Based Access Control (RBAC): Mengimplementasikan sistem otentikasi JWT dengan 3 tingkat otorisasi yang berbeda (Employee, Manager, HR).
  • Business Logic Protection: Memprogram validasi di sisi backend (Express.js) untuk memblokir pengajuan cuti yang tanggalnya tumpang tindih serta mencegah saldo cuti bernilai minus.
  • Premium UI/UX Design: Mengembangkan antarmuka responsif menggunakan React dan Tailwind CSS dengan prinsip desain korporat modern (Glassmorphism, palet warna elegan, dan transisi animasi mulus).
  • Zero-Error Tracking: Sistem berhasil memastikan penghitungan hari cuti 100% akurat karena dikalkulasi secara otomatis oleh server.
  • Efisiensi Manajerial: Mengurangi waktu pemrosesan persetujuan cuti secara drastis melalui Manager Dashboard.
  • Struktur Kode Skalabel: Aplikasi dapat dikembangkan lebih lanjut tanpa error berarti berkat penggunaan pola arsitektur RESTful API dan Type-Safety dari TypeScript.

Customer Churn Intelligence

Problem:

Bayangkan Anda menjalankan bisnis SaaS — setiap bulan ada pelanggan yang diam-diam pergi tanpa pernah bilang kenapa. Tim Customer Success baru sadar ketika pelanggan sudah cancel. Padahal, mencari pelanggan baru itu 5-7x lebih mahal dibanding mempertahankan yang sudah ada. Masalahnya sederhana: tidak ada cara untuk tahu siapa yang akan pergi sebelum mereka benar-benar pergi.

Action & Result:

Untuk menjawab tantangan ini, saya membangun sebuah platform Machine Learning dari nol — bukan sekadar model di Jupyter Notebook, tapi sistem yang siap digunakan di dunia nyata. Platform ini bisa memprediksi peluang churn setiap pelanggan secara real-time, mengelompokkan mereka ke level risiko (HIGH / MEDIUM / LOW), lalu memberikan rekomendasi aksi yang spesifik — misalnya "hubungi pelanggan ini untuk review pembayaran" atau "tawarkan upgrade plan". Seluruh sistemnya saya rancang end-to-end: mulai dari pipeline data (5 sumber CSV → cleaning → 22 fitur baru), model XGBoost yang sudah di-tuning, REST API via FastAPI, dashboard Streamlit untuk tim non-teknis, database logging untuk audit trail, hingga Docker untuk deployment.

  • 0.8553 ROC-AUC Score
  • 92.77% Recall (Churn)
  • 22 Engineered Features
  • 5 Data Sources

Key Highlights:

  • Pipeline ML dari Hulu ke Hilir: Saya membangun seluruh alur kerja — dari membuat data sintetis, membersihkannya (duplikat, umur negatif, typo), menggabungkan 5 tabel menjadi satu dataset analitis, merekayasa 22 fitur baru, melatih model XGBoost dengan hyperparameter tuning, hingga menyajikannya lewat REST API.
  • Mendeteksi "Kebocoran Data" yang Berbahaya: Awalnya model saya mencapai akurasi 99.9% — terlalu sempurna untuk dipercaya. Setelah saya investigasi, ternyata ada 2 fitur yang "menyontek" jawaban (target leakage). Saya hapus keduanya, dan hasilnya turun ke 0.855 — angka yang jauh lebih jujur dan bisa diandalkan.
  • Memilih Threshold yang Masuk Akal Secara Bisnis: Saya sengaja menggunakan threshold 0.40 (bukan default 0.50). Alasannya? Dalam konteks churn, lebih baik salah menandai pelanggan sehat sebagai berisiko — kita cukup telepon mereka untuk check-in — daripada melewatkan pelanggan yang benar-benar akan pergi.
  • API yang Siap Produksi: FastAPI dengan 4 endpoint utama, Swagger docs otomatis, feature engineering langsung di server (bukan di client), dan desain yang tetap jalan meskipun database logging gagal — prediksi tetap dikembalikan ke user.
  • Rekomendasi Aksi yang Bisa Langsung Dieksekusi: Platform tidak hanya bilang "pelanggan ini berisiko tinggi", tapi juga memberikan saran konkret: apakah perlu review pembayaran, sesi onboarding ulang, assign dedicated support, atau tawarkan diskon kontrak tahunan.
  • Dashboard untuk Tim Non-Teknis: Streamlit dashboard yang intuitif — tim Customer Success cukup isi form profil pelanggan, klik tombol, dan langsung lihat hasilnya dengan indikator warna hijau/kuning/merah beserta rekomendasi aksinya.
  • Siap Deploy dengan Docker: Seluruh sistem dikemas dalam Docker Compose — API dan PostgreSQL berjalan di container terpisah dengan health check dan persistent volume, tinggal docker compose up dan selesai.
  • Teruji dengan Automated Testing: Saya menulis test suite menggunakan Pytest yang mencakup seluruh lapisan — dari data cleaning, validasi bisnis, training model, hingga API endpoints — untuk memastikan tidak ada yang rusak saat dikembangkan lebih lanjut.
